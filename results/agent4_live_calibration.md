# Agent 4 live-format duplicate threshold calibration

Generated by `scripts/run_agent4_live_calibration.py`. Do not edit by hand. Recommendation only: settings are unchanged.

## 1. Limitations (read first)

- **Synthetic labels.** Every label comes from `scripts/augment_tickets.py` or the hand-written calibration set (`scripts/build_agent4_calibration_set.py`), both written for this project, not real ITSM history.
- **30 positives** (5 AUG-DUP + 25 CAL-DUP), so one ticket moves duplicate recall by about 3.3 points.
- **Single Agent 1 run per ticket** (`gemini-3.5-flash-lite`, temperature 0). Run-to-run extraction variation is not included yet; the variation check (`scripts/check_agent1_variation.py`) is pending.
- **Building unknown.** Agent 1 does not extract a building today, so building-based separation never applies to duplicates.
- **Specific to all-MiniLM-L6-v2 and this field format** (`build_kb_query` lines). A prompt, field or embedder change invalidates these numbers.

## 2. Protocol

- Tickets: 230 (background 122, cluster_member 48, duplicate 30, hard_negative_building 5, hard_negative_category 5, hard_negative_near_miss 15, hard_negative_time 5).
- Query: `build_kb_query(cached Agent 1 category, cached fields)`; no building. Pool tickets: `seed_to_record()` plus `correlation_text = build_correlation_text()` from the same cache (None when no field has a value -> engine falls back to title + description).
- Temporal leave-one-out: each ticket queries the pool minus itself, engine clock at its own created_at.
- Real `CorrelationEngine`: category-agreement bonus 0.05, cross-category duplicate needs raw >= 0.95, lookback 72h, cluster threshold 0.7 / min count 3 / window 6h (settings defaults). Only `dup_threshold` is swept, 0.60-0.98 in 0.01 steps; texts are embedded once.
- Expected: duplicate -> DUPLICATE of `duplicate_of`; 20 detectable cluster members -> INCIDENT_CLUSTER (28 early members neutral); everything else, near-misses included, -> NO_MATCH.
- DUPLICATE decision: RAW cosine >= dup_threshold, among candidates allowed by the minimum-field gate (query and candidate correlation_text need >= 2 field lines; candidates without correlation_text stay eligible) and the cross-category rule. The ranking score is raw + 0.05 when the cached Agent 1 category equals the ticket's stored category (capped at 1.0); it orders candidates and counts for clusters only.

## 5. Recommendation

### Strict rule

Rules applied mechanically to the 0.01 sweep:

1. **0 DUPLICATE-caused FP on all hard negatives** (building, time, category, near-miss): 1/39 thresholds pass - 0.98.
2. **Background DUPLICATE-caused FP rate <= 1%**: 1 of those pass - 0.98.
3. **Highest duplicate recall** among them is 0.1000, reached at 0.98; the tie goes to the higher (more conservative) threshold: **0.98**.

Judgements behind the rules:

- Rules 1-2 count **DUPLICATE-caused** FPs only. INCIDENT_CLUSTER FPs depend on the cluster threshold (0.7), which this sweep does not change; they are a cluster-threshold issue, shown in their own columns and called out below.
- **Cluster members called DUPLICATE** are reported but kept out of rules 1-2: a cluster member merged into a sibling's ticket is the same incident, a lesser error than merging a different issue.

4. **Margin at 0.98:** lowest true-original score still caught = 0.9831; highest top score among hard negatives + background = 0.9821 (TEAMS-013); highest among all non-duplicates (cluster members included) = 0.9821 (TEAMS-013).

Strict-rule threshold: 0.98 (not adopted - see section 7).

### Suggestion rule

A DUPLICATE is now a suggestion the user confirms before anything is merged, so a wrong suggestion costs one extra question rather than a wrong merge. Rule: the HIGHEST threshold with duplicate recall >= 0.90.

Thresholds with duplicate recall >= 0.90: 0.60, 0.61, 0.62, 0.63, 0.64, 0.65, 0.66, 0.67, 0.68, 0.69, 0.70, 0.71, 0.72, 0.73, 0.74, 0.75, 0.76, 0.77, 0.78, 0.79, 0.80, 0.81, 0.82, 0.83.
The highest is **0.83**: recall 0.9000 (27/30), 57 wrong suggestions = **28.5 per 100 non-duplicate tickets** (200 non-duplicate queries; a wrong suggestion is any wrong DUPLICATE call, which the user is now asked to confirm).

Margin at 0.83: lowest true-original raw score still caught = 0.8331; highest eligible raw score among hard negatives + background = 0.9821 (TEAMS-013).

Suggestion-rule threshold: 0.83 (not adopted - see section 7).

## 7. Adopted threshold

`corr_dup_threshold` = **0.87** (app/config/settings.py; previously 0.95). Neither mechanical rule's value is used; the choice is the knee of the recall curve.

| threshold | duplicates caught | wrong suggestions | per 100 non-duplicates | note |
|---|---|---|---|---|
| 0.83 | 27/30 | 57 | 28.5 | suggestion rule; asks too often |
| 0.87 | 25/30 | 37 | 18.5 | adopted: last value before recall drops sharply |
| 0.89 | 20/30 | 29 | 14.5 | recall 0.83 -> 0.67 within 0.02 (0.88 alone loses 3 duplicates) |
| 0.95 | 11/30 | 7 | 3.5 | previous default; misses most duplicates |

- Why 0.87: going from 0.83 to 0.87 removes 20 wrong suggestions and costs only 2 real duplicates; above 0.87 every step loses real duplicates quickly.
- Why not 0.98 (strict rule): it catches 3 of 30 duplicates and its margin (0.001) is noise, not a real separation.
- Wrong suggestions were measured on a deliberately hard set built to be full of look-alikes; they are not an expected live rate.
- A wrong suggestion now costs the user one Yes/No question, not a wrong merge - the trade-off the confirmation step exists for.
